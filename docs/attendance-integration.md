# 补卡前后端接入计划（方案B）

## 一、目标
- 前端通过 Zustand 与 MSW 对齐后端接口，先完成页面联调
- 开发阶段所有请求走 `/api` 且被 MSW 拦截，数据来自 `mock/data.json`
- 不接入审批系统与打卡系统

## 二、方案对比与选择
### 方案A：页面本地状态 + 直接写 mock
- 优点：改动少，上手快
- 缺点：状态分散，后续联调与复用成本高

### 方案B：Zustand Store + MSW Handlers + 接口对齐
- 优点：结构清晰，前后端一致，后续联调成本低
- 缺点：改动面更大

选择：方案B

## 三、开发里程碑
1. 接口对齐：确认 `/attendance/...` 路径与请求/响应结构
2. 状态管理：新增 `use-attendance-store` 管理设置与记录
3. 页面改造：补卡页面仅负责渲染与交互
4. Mock 接入：补齐 `handlers` 与 `data.json`
5. 联调验证：加载、保存设置、保存记录、删除记录全链路
6. 体验校验：进度条颜色、去重、锁定、表单校验

## 四、边界与风险
- 月度锁定：由 `last_pushed_month` 决定
- 未来日期与跨月：前端提前拦截
- 推送日期超出当月：显示为最后一天，后端以最后一天执行
